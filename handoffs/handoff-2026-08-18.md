## BUG — duplicate `track:` directives accumulate in .rollnotes.json

Found in `albums/compositions/nightroll/cool-bmaj-progression.rollnotes.json`
at commit `df3d344`:

```json
{"at":[1,1],"type":"track","track":"pulse1","voice":"sawtooth"},
{"at":[1,1],"type":"track","track":"pulse1","voice":"sawtooth","vol":1.1},
```

Two directives for the same track, identical except the second carries
`vol`. **Josh has never hand-edited an annotation file** — this is
generated. Same shape as the duplicate-notes problem cleaned up yesterday,
different subsystem.

### Diagnosis (read from source, needs confirming by repro)

`saveVoices()` (index.html ~3796) is written as an upsert:

```js
rollnotes = rollnotes.filter(n => !(n.trackdir && n.trackdir.name.toLowerCase() === name.toLowerCase()));
// ...then push the new directive with added: true
```

The round-trip is fine — `parseRollnotesJSON` → `jsonToRawNote` →
`deriveNoteTypes` does populate `n.trackdir` on loaded notes, so the filter
does match them. **The removal is in-memory only.**

`saveLocalNotes()` (~1935) persists *only* added notes:

```js
const local = rollnotes.filter(n => n.added).map(...)
```

So when the filter drops a directive that was already **synced** (committed,
`added: false`), nothing records that it was deleted. There is no tombstone —
localStorage holds added notes exclusively. On the next load the committed
directive returns from the repo file, and the newly-added one is also
present. Result: two directives for one track.

This predicts exactly the observed pair: the first pulse1 entry is the
earlier committed state (voice only), the second is the later in-session
change (voice + vol).

### Suggested repro

1. Set a track's voice, Save/commit.
2. Reload.
3. Change that same track's volume.
4. Inspect the .rollnotes.json — expect two directives for that track.

### Why it hasn't bitten yet

`finalizeNotes()` applies directives in array order, so the later entry wins
and playback sounds correct. It's silent accumulation: one extra entry per
edit-after-commit cycle, per track. Worth fixing before someone tunes a mix
over several sessions and ends up with a dozen.

### Fix direction (Claude Code's call)

The general problem is **deletion of synced annotations has no persistence
path**. Options: a tombstone list in localStorage that the loader subtracts;
or de-duplicating directives at load (last-wins by track name) as a cheap
guard. The general fix is better if deleting other synced annotation types
has the same hole — worth checking, since the help text claims "Delete works
on synced notes too (permanent on Sync)."

Note the same file also has `{"at":[1,1],"text":"lane: 37"}` with no `type`
field, while everything else is typed. Probably harmless, but the mixed
representation is worth a look while in here.

## CONCEPT — context-aware drum generation (Josh, 2026-08-19)

**Status: DESIGN STAGE. Do not implement.** Josh explicitly wants design
work before any code. Logged because he likes the idea and doesn't want it
lost.

**Reference point:** Logic's Drummer tracks — XY pad (loud/soft ×
simple/complex), per-instrument busyness controls, fills knob, swing, and
crucially the ability to *follow another track* (align kick to the bass).
Generative and section-aware rather than a repeating loop: it knows where a
phrase ends and puts a fill there.

**Why Night Roll is well positioned:** Logic INFERS structure. Josh
DECLARES it. Sections, chord spans, and loop points are already annotated
data, so a generator here can be structurally aware without guessing.

### Capability sketch, roughly in value order

1. **Section-aware fills.** Fill in the last bar before a section boundary,
   crash on the downbeat after. Pure lookup against existing annotations,
   and it's most of what makes programmed drums sound intentional.
2. **Follow the bass.** Align kick to bass onsets. Matters especially on
   `cool-bmaj-progression`, where the bass is the melodic driver.
3. **Harmonic-rhythm awareness.** Josh's chord spans start on beat 4, not
   beat 1. A generator that accents chord CHANGES rather than barlines
   reads as musical and is just arithmetic.
4. **Density controls.** Complexity parameter over hat subdivision, ghost
   notes, fill frequency. The XY-pad idea with axes chosen for this
   material.

### The generate-and-judge model — Josh's framing

He doesn't have the drum vocabulary to write interesting parts himself, but
he can evaluate instantly: *"I know what sounds good. I just don't have the
ability right now to do it myself."* Same division of labor that worked for
instrument voices tonight — he couldn't reason to "trumpet not violin," he
auditioned and knew in a second. Generation is the bottleneck; evaluation
is cheap. So: generate with randomness, let him reroll.

**Design requirements that follow from that:**

- **Reroll is ONE action; undo is ONE step.** He'll do it twenty times in a
  row. The existing 🥁 drum fill already collapses to one undo — same
  pattern.
- **Seeds.** Every generation carries a number so a take three rerolls back
  is recoverable. Without this he WILL lose one he liked, which is exactly
  the soundfont-race frustration from 08-17 repeating in a new place.
- **Constrained randomness, not free.** Fixed skeleton (backbeat, downbeat
  kick) with variation only in negotiable parts: hat subdivision, ghost
  notes, kick placement between anchors, fill selection from a small
  vocabulary. Every roll should be plausible — he should be choosing among
  good options, not filtering out garbage.
- **The fill vocabulary is where taste gets solved empirically.** Start
  with a handful; keep what he picks often, cut what he always skips.

**Honest caveat to carry into design:** placing a fill in the right bar is
tractable; whether it's a GOOD fill is a taste problem, and drum taste is
the knowledge Josh says he's missing. Expect heavy iteration on the fill
vocabulary. The structural half — right place, right density, aligned to
what the song is doing — is the part that's genuinely solvable and is also
what separates programmed drums from convincing ones.

## FEATURE REQUEST — attached text notes on ALL annotation types (Josh, 2026-08-19)

The mechanism already exists, but only for chords. index.html ~1660:

```js
const cm = n.text.match(/^chord:\s*(.+)/s);
if (cm) { // first line = symbol; any further lines = attached note
  const body = cm[1].split("\n");
  n.text = body[0].trim();
  const note = body.slice(1).join("\n").trim();
  if (note) n.cnote = note;
}
```

**Sections actively discard it** — line ~1658 takes `split("\n")[0]` and
throws the remainder away. Keys and time signatures have no note path at
all.

**Generalize the pattern:** first line is the value, remaining lines are
the attached note, for every annotation type — section, key, timesig,
tempo, loop, track. Rename `cnote` → `note` since it stops being
chord-specific. The ☰ Notes list should indicate which entries carry one
so they're findable.

**Why it matters — Josh's own argument.** The tool stores findings but
can't verify them; it will record a wrong chord as faithfully as a right
one. The attached note is where the *doubt* lives, and doubt is what makes
an open question findable later. Prologue 6.1 has stayed workable for days
precisely because the uncertainty got written down alongside the answer.

**Motivating case: floating castle.** Josh knows the tonic (B♭) and has
determined the material is whole-tone. "There is no key in the conventional
sense" is a real finding with nowhere to live right now. The `key:` partial
syntax (`B♭?`) stores a tonic with the mode pending — but it cannot store
WHY it's pending. The app records uncertainty without the reasoning, which
is the half worth keeping.

Not every annotation needs one. Josh: when he's confident the key is C, he
just won't fill it in.

## FEATURE REQUEST — deterministic query tools in `tools/` (2026-08-18)

**Motivation.** Web sessions clone the repo and run scripts in a bash
container — `dump_notes.mjs` produced every note listing this session. But
anything beyond a raw dump gets hand-rolled inline, badly. Claude made
multiple factual errors this session by eyeballing dumps: asserted a chord
at 6.3 spanned two beats when the evidence was split, and claimed an E in a
stack that wasn't there. Both were reasoning-over-text failures, not missing
data. A deterministic script returns the right answer every time and removes
that entire error class.

Also worth noting Claude hand-wrote an old-vs-new note diff in Python twice
tonight. A repo version would be correct by default rather than by luck.

**Not a web API.** Josh floated a server; the transport buys nothing, since
scripts in the repo are already reachable from any session that clones. No
server, no network, versioned with everything else, and useful to Josh
directly from a terminal.

**Design principles**

- Deterministic and dumb. Report what IS. Never name a chord, infer a key,
  or classify a note as passing vs. chord tone — those are Josh's findings
  and a tool that guesses them corrupts the methodology.
- De-duplicate by default (`--raw` to disable), given the duplicate-note
  history.
- `--json` on everything, so output is parseable rather than re-parsed
  from prose.
- Take `album/song` or a path; resolve `.mid` + `.rollnotes.json` together.

**Proposed commands**

```
tools/at.mjs <song> <bar.beat> [--span <bar.beat>]
```
Everything sounding at that moment, per track, distinguishing notes that
ONSET there from notes still ringing from earlier (the onset-vs-full-span
distinction that broke prologue 5.3 — the tool should make it structural).
Returns: track, pitch, onset beat, duration, whether it starts or sustains.

```
tools/span.mjs <song> <from> <to>
```
All events in a range, grouped by track, with a pitch-class set for the
span. Pitch-class set only — NOT a chord name.

```
tools/loop-targets.mjs [song|--all]
```
For each song: loop point, target, and what every track plays at the
target. Directly serves the loop-target tonic methodology, and `--all`
makes it a corpus sweep.

```
tools/pitch-census.mjs <song> [--track T]
```
Every pitch class present, with counts and total sounding duration, plus
which are ABSENT. The "no A# anywhere" observation about
`cool-bmaj-progression` came from Claude noticing by hand; this makes it a
one-liner. Duration-weighted matters — a pitch appearing once as a 16th is
different from one appearing as six half notes.

```
tools/song-diff.mjs <old.mid> <new.mid>
```
Per-track added / removed / changed, de-duplicated, grouped by bar. Used
twice tonight, hand-written both times.

```
tools/annotations.mjs <song> [--type chord|section|key|...]
```
Dump annotations resolved to bar.beat with spans, and **flag anomalies**:
chords in section fields (the prologue 5.3 bug), duplicate track
directives (the bug above), spans whose content changes mid-span, and
annotations pointing at bars that don't exist.

**Other groups worth considering**

- `tools/harmonic-rhythm.mjs` — where chord spans start, and whether the
  song is consistent. Would have surfaced `cool-bmaj-progression`'s
  beat-4-displaced harmonic rhythm mechanically instead of by eye.
- `tools/onset-grid.mjs <song> <bar>` — onset positions as subdivisions of
  the bar, for meter work. The 3/4-vs-6/8 shop question was exactly "which
  eighths carry onsets," answered by hand.
- `tools/track-role.mjs <song> <track>` — for a given track, at every
  settled chord span, whether its notes are IN the annotated chord, with
  durations. Reports membership only, never conclusions. This is the
  twenty-minute pulse-2 investigation as a script. **Caveat: it reads
  Josh's own chord annotations, so it's only valid where those are already
  settled — must refuse or warn on unannotated spans rather than silently
  comparing against nothing.**
- `tools/section-compare.mjs <song> <sectionA> <sectionB>` — the A/B
  contrast dimensions as raw numbers: pitch range per section, onset
  density, harmonic rhythm rate, pitch-class sets and their difference.
  Serves the queued B-part study directly. Reports measurements; the
  interpretation stays Josh's.

**The line that matters:** these tools should make it impossible to get a
FACT wrong, and impossible to get a FINDING handed to you. Everything above
reports what is in the file. None of it concludes.

**Build on the existing harness, do NOT write a second parser.**
`tests/harness.mjs` already extracts the inline script from `index.html`
and runs it in a Node VM with a DOM stub — `dump_notes.mjs` imports
`createApp` from it. So `parseRollnotesJSON`, `jsonToRawNote`,
`deriveNoteTypes` and `finalizeNotes` are all callable from Node with no
build step. These scripts should be thin wrappers: load the song through
the harness, read the enriched note objects (`trackdir`, `chord`,
`section`, `start`, `end`, `depth` already resolved), print. This also
guarantees the tools agree with what Josh sees on screen; an independent
parser could drift.

## REDESIGN — sections and chords get their own lane groups (Josh, 2026-08-18)

Josh's call, and it deletes the equal-span bug above rather than patching
it. **Sections and chords should never share a row.**

- Sections occupy their own row group; chords occupy theirs.
- A group with nothing in it shows no row at all.
- Both present → both groups show.

Consequence: equal spans become structurally incapable of colliding, and
the depth tie-break discussed above is never needed. `RULER_H` becomes the
sum of two independently-computed groups.

**Preserve:** sections still NEST by containment — Overworld has `A`
containing `A1` and `A2`, so the depth logic doesn't disappear, it just
runs independently inside the sections group. Chords presumably never nest,
so that group is likely always exactly one row.

This supersedes the tie-break fix suggested in the bug entry above — do the
redesign instead.

**Conventions to implement:**

## BUG — chord band renders on top of a section band when spans are identical

Reported by Josh 2026-08-18: the Intro chord (B) draws over the Intro
section band instead of below it. Every other chord in the song lays out
correctly.

### Diagnosis (index.html ~1879)

```js
s.depth = secs.filter(t => t !== s && t.start <= s.start && t.end >= s.end &&
                           (t.start < s.start || t.end > s.end)).length;
```

Depth = how many bands STRICTLY contain this one. The final clause requires
the container to be strictly larger on at least one side, so **two bands
with exactly equal spans do not contain each other** — both get depth 0 and
both draw into the same lane at `BASE_RULER_H + depth * LANE_H` (~2789).

In this song: section `Intro` is 1.1–2.3 and chord `B` is 1.1–2.3.
Identical. Collision. The other chords are strict subsets of the `A part`
section (2.4–6.3), so containment is unambiguous and they lay out fine.

### Fix direction

Josh explicitly does NOT want the workaround (nudging one span so they
differ) — fix the layout rule.

Suggested: break ties by type. When a section and a chord share an exact
span, the section is the larger structural idea and should own the upper
lane; the chord goes below. E.g. count an equal-span section as a container
when computing a chord's depth. Care needed so that two sections with equal
spans, or two chords with equal spans, still behave sensibly (probably
stable order by array position).

Not specific to this song — any section containing exactly one chord hits
it, which will be common on short sections and on B-part work.

Note `hitTest` at ~3494 finds bands by `n.depth === lane`, so fixing depth
also fixes tapping the wrong band in the collided lane.
