## The general principle (Josh's, this session — for glossary.md)

**Two kinds of movement: rhythmic and harmonic. As a default, don't
have independent voices doing the same kind at the same time.**

Worked example in bars 15–16: the bass is steady quarters but moving
structurally; the upper voices vary rhythmically (pulse1 sixteenths,
pulse2 eighths) but hold one harmony. Each layer moves in exactly one
dimension. Note this is the *inversion* of the A section, where the
bass was the busy eighth-note bounce.

Josh flagged both halves as defaults with exceptions. The exceptions,
stated precisely:

- **Rhythmic:** cross-rhythm works when one layer stays steady —
  triplets over eighths. This is his existing steady-layer principle
  from Cool Bmaj, and it is a *rhythmic* rule.
- **Harmonic:** voices moving in *different directions* is NOT the
  chaotic case — contrary motion is prized voice-leading. The actual
  failure mode is voices implying *different chords at the same
  moment*, which stays a problem regardless of direction.

That correction matters: the rule as first stated would have excluded
contrary motion along with the genuinely bad case.

# BUG — duplicate key annotations at the same anchor (Josh, 2026-08-25)

**Symptom.** Josh set `F mixolydian` at 1.1 on a song that already had
`key F` at 1.1 from an earlier session. Instead of replacing it, the app
added a second key annotation at the same anchor. Both are now committed
in `airship.rollnotes.json`. Josh's rule: **there should never be two key
annotations at the same point in a song** — setting a key at an anchor
that already has one is an edit, not an insert.

**Cause.** `index.html`, `dropLocalKeyAt(bar)` (~line 2473):

```js
function dropLocalKeyAt(bar) { // a new key change replaces any local key marker at the same bar
  rollnotes = rollnotes.filter(n => !(n.added && n.keydir !== undefined && n.b1 === bar));
}
```

The dedupe is called from both key-setting paths — the `keysetBtn`
handler (~7228) and the note-dialog `type === "key"` branch (~9495) — so
the wiring is right. The predicate is wrong, in two independent ways:

1. **`n.added` is the bug Josh hit.** Only annotations created in the
   current session carry `added: true`; the flag isn't serialized, so
   anything loaded from a committed `.rollnotes.json` lacks it. The
   dedupe therefore only ever replaces keys from the same session and is
   structurally incapable of replacing a key that was previously synced.
   The comment ("any *local* key marker") suggests this was deliberate at
   some point, but it produces exactly the duplicate Josh is reporting.

2. **`n.keydir !== undefined` misses tonic-only keys.** The partial form
   stores `keypartial` and leaves `keydir` unset (both paths do this for
   the "tonic, no mode" case). So a `F?` marker is never dropped, and
   setting a real key over one leaves both. Elsewhere the codebase
   consistently tests `n.keydir !== undefined || n.keypartial` — e.g. the
   KEY filter at 7954, `governingAt` at 2617, the drag handler at 3665.
   This predicate is the odd one out.

**Also worth deciding:** the match is on `b1` only, ignoring `q1`. The
button path always writes `q1: 1`, but the note-dialog path takes `q1`
from the dialog, so a key at 3.1 and a key at 3.3 are possible — and the
current code would drop the wrong one. Josh's stated rule is "the same
point in the song," which reads as anchor, not bar. If keys are meant to
be bar-level only, the dialog should refuse a non-1 beat; if they're
anchor-level, the filter needs `q1` in it. **Needs Josh's ruling before
the fix, since it changes what the annotation format means.**

**Suggested predicate**, pending that ruling:

```js
n.keydir !== undefined || n.keypartial   // both key forms
&& n.b1 === bar                          // (+ n.q1 === q1 if anchor-level)
// drop the n.added test entirely
```

**Data cleanup.** Once fixed, `airship.rollnotes.json` still has the
stale `key F` at 1.1 alongside `F mixolydian`; it needs removing by hand.
Worth a scan of the other 18 FF1 songs for the same duplication — any
song whose key was revised across two sessions could have it.
